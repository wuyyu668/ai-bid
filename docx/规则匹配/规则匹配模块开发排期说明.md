# 规则匹配模块开发排期（5 天 · 测试先行 + 真实标书盲测）

> 框架：**Day 1 测试先行 + 引擎骨架；Day 2 规则库（TDD）+ LLM 辅助生成；Day 3 Golden Standard 质量验证；Day 4 真实标书盲测（泛化验证）；Day 5 按盲测意见修改规则 + 回归 + 收尾。**


## 总体分工

规则引擎与 Multi-Agent 审核的边界：

| | 规则引擎 | AI Agent |
|---|---|---|
| 处理什么 | 确定性、可模式化的问题 | 语义复杂、需要推理的问题 |
| 速度 | < 50ms / 百页文档 | ~30s |
| 成本 | 零 API 调用 | 数千 tokens |
| 可复现 | 100% 可复现 | 有随机性 |
| 误报策略 | 宁可误报，不可漏检（Recall > 95% 铁律） | 精确度优先 |

判断标准：**能用"是/否"回答的 → 规则引擎；需要语义理解的 → Agent。** 规则引擎的输出不是终端报告，而是 Agent 的 System Prompt 上下文。

---

## 贯穿原则：测试驱动开发（TDD）

三层测试内容在 **Day 1 编码前确定**，开发过程中先行：

| 层级 | 内容 | 作用 |
|---|---|---|
| ① 单元测试 | 六要素 schema 校验、三型匹配器（regex/keyword/field_compare）、conditions 优先级、YAML 容错加载 | 约束引擎行为，随代码即写即验 |
| ② 回归测试集 | Golden Standard（人工标注，3 份文件 × 20+ 条） | 规则质量衡量 + 回归守门（Recall 不得下降） |
| ③ 泛化盲测集 | **真实标书**，来源与开发集零重叠，冻结哈希 | 验收泛化能力（Day 4 首轮 / Day 5 复测） |

TDD 循环（每一条规则、每一个匹配器都遵循）：

```
写失败测试（红）→ 最小实现（绿）→ 重构（保持绿）
```

**重要边界**：② 是开发/回归集，③ 是验收集。③ 不得作为规则调优样本，一次冻结一次正式运行（参考 `benchmark/blind-v2` 冻结规则：SHA-256 校验，任一文件改变即中止盲测）。

### 六要素规则模型

```yaml
rules:
  - id: "DISC-001"                    # ① 唯一 ID
    category: "排斥性条款"             # ② 问题分类
    industry: "建筑工程"               # ③ 行业（决定何时触发，防 40% 误报）
    severity: "critical"               # ④ 严重程度
    source:                           # ⑤ 来源追溯
      law: "中华人民共和国招标投标法"
      article: "第十八条"
      version: "2017年修正版"
      effective_date: "2017-12-28"
      excerpt: "招标人不得以不合理的条件限制或者排斥潜在投标人..."
    conditions:                       # ⑥ 适用条件（不是全局扫描）
      document_type: "招标文件"
      project_types: ["施工招标", "工程总承包"]
      trigger:
        chapter_keywords: ["投标人资格", "投标人须知"]
      exclude:
        project_types: ["国际招标"]
    patterns:                         # ⑦ 匹配模式（多模式互补）
      - type: "regex"
        value: "(投标人|潜在投标人).*(注册地|设立.*机构).*(本市|本省|本地|辖区)"
      - type: "keyword"
        value: ["排斥", "限制", "差别待遇", "歧视"]
    check: "any_match"                # ⑧ 判定逻辑：any_match / all_match
    suggestion: "该条款存在地域限制，可能违反《招标投标法》第十八条..."
    law_ref: "《中华人民共和国招标投标法》第十八条"
```

### 三合一匹配引擎

- **regex**：预编译缓存，YAML 里 `\uXXXX` 自动转 `\x{XXXX}`（`normalize_regex`）；单条正则编译失败只跳过该条并告警，不让整库加载失败
- **keyword**：字符串数组 OR/AND；`match_mode: absence` 支持"缺失匹配"（如资质章节缺少"安全生产许可证"）
- **field_compare**：文档级度量比较，`left/operator/right`，right 支持表达式如 `估算价 * 0.02`；操作数解析失败保守返回 false（不误报）
- **conditions 优先级**：exclude > document_type > trigger
- **check**：`any_match` / `all_match`（`all_match` 防"仅出现中标字样即误报"）

> TDD：每个匹配器先写"正例命中 / 负例不命中 / 边界（空值、异常表达式、编译失败正则）"用例，实现通过后再进入下一项。

### 与 Agent 的接口（本日核心交付）

- [CRITICAL] 排斥性条款 (DISC-001): ... 
  依据: 《中华人民共和国招标投标法》第十八条
  建议: ...

## 需要深度语义审查的条款
以下条款不在规则引擎的覆盖范围内，请进行语义分析：

## Day 2 — 规则库（TDD）+ LLM 辅助生成规则

### 目标

**每条规则先写匹配用例，再落库。** 用 DashScope（qwen-plus）从法规全文批量提取候选规则，经静态校验后落 draft，人工确认转正。

### 任务清单

| 文件 | 内容 |
|---|---|
| `rules/*.yml` | 补齐 25-30 条，六要素完整，覆盖 DISC/QUAL/EXPR/PRIC/TIME/SAFE/PROC 类别 |
| `rules/*.rs` 规则级用例 | 每条规则配套"应该匹配 / 不该匹配"用例（正负例），随规则进回归测试集 |
| `agents/tools/generate_rule.rs` | LLM 生成规则工具 |
| `agents/prompts.rs` | 规则提取 Prompt 模板 |
| `rules/validator.rs` | `RuleValidator` 静态校验 5 项 |
| `api/router.rs` + `api/handlers.rs` | `POST /api/v1/rules/generate` |

### Prompt 设计

- 强约束输出 YAML，字段与六要素模型一致
- **Few-shot 3 例**：2 正（资质类 + 排斥性类）+ 1 负（"这条法条不适合转规则，因为..."）
- 关键提醒：正则特殊字符转义、适用条件必填、`source.excerpt` 必须法条逐字摘录
- 复用 `services::llm_client.rs` 的 dashscope 协议

### RuleValidator 静态校验清单

1. 法条名称存在性（对照本地法规清单，本项目无 Neo4j）
2. 条款编号存在性（`第十八条` vs `第18条` 需归一化）
3. 正则语法可编译
4. `conditions.trigger` / `exclude` 自洽（不矛盾）
5. `industry` 值在分类体系内（建筑工程/政府采购/IT/通用）

**AI 最高频 4 错**（校验重点）：法条名称不准确 / 条款编号格式错 / 正则未转义 / `conditions` 缺失。

### 流程

```
法规全文 → LLM 批量提取 → RuleValidator 校验 → 通过落 rules/_drafts/ → 人工确认（先补匹配用例再转正）→ 正式库
                                      └─ 不通过 → 带错误标记，人工修正
```

> TDD：AI 生成的候选规则转正前，先为其编写"应该匹配 / 不该匹配"用例；用例通过后规则才能 `enabled: true`。

### 覆盖率分析

对比 AI 提取规则集 vs Day 1 手写规则集，识别 AI 盲区（约 29%）：跨多条法条推断 / 行业知识（资质等级体系）/ 案例关联（串通投标模式）。AI 辅助加速初稿，不替代人工。

### 验收

- [√] 25-30 条规则六要素完整，**每条规则配套正负例用例**并进回归测试集（27 条规则 × 正负例 1 组 → `rules/cases.json` → `tests/rules_cases.rs` 3 测试全绿）
- [√] 用一段含保证金金额的文本生成候选规则，能落 `rules/_drafts/`（`generate_rule` 工具：LLM 草稿 → RuleValidator 校验 → 落盘；离线 mock 模式验证落盘路径，真实 LLM 需有效 `DASHSCOPE_API_KEY`）
- [√] 校验通过率 > 80%（离线 mock 实测 7/8 = 87.5%，`bin/eval_rule_generation.rs --offline`；在线评测需有效 key）

## Day 3 — 质量验证（Golden Standard 回归）

### 目标

构建人工标注的 Golden Standard，用数据衡量规则质量（混淆矩阵 + Recall/Precision），并检测规则冲突。**这是开发/回归集，不是泛化验收集。**

### 任务清单

| 文件 | 内容 |
|---|---|
| `golden/expected_matches.json` | 人工标注集（回归测试资产） |
| `rules/validator.rs`（扩展） | `RuleEval`：tp/fp/fn 混淆矩阵 + recall/precision/f1 + `detect_conflicts` |

### Golden Standard 构建（lesson-03）

```json
[
  {
    "document_id": "doc_sha256_xxx",
    "clause_id": "cl_a3f2b1c8",
    "clause_text": "投标人须在本市注册成立三年以上",
    "expected_rules": [
      {"rule_id": "DISC-001", "should_match": true},
      {"rule_id": "QUAL-003", "should_match": false}
    ]
  }
]
```

- 标注粒度：`(clause_id, rule_id)` 对
- 工作量：3 份招标文件 × 20+ 条"应该匹配"标注 + 抽查 10 条"不应该匹配"验证
- 产出即**回归测试集**：此后每次加规则/改规则都重跑，Recall 不得下降

### 指标与铁律

| 指标 | 门槛 |
|---|---|
| Recall | **> 95%（铁律：宁可误报，不可漏检）** |
| Precision | > 80% |
| F1 | 计算并按类别分列 |
| 规则冲突 | 0 条未解决 |

### 误报根因分析（Top-N 修复）

| 根因 | 占比 | 示例 | 修复 |
|---|---|---|---|
| 未加行业分类 | 40% | "施工总承包资质"在 IT 采购触发 | 加 `industry` |
| 未加触发条件 | 25% | "排斥性条款"在"定义"章节触发 | 加 `trigger.chapter_keywords` |
| 正则过宽 | 20% | `.*限制.*` 命中"不受限制" | 正则加否定断言 `(?<!不)限制` |
| 关键词单字命中 | 15% | "要求"在非法律语境命中 | 用分词替代裸 contains |

### 验收

- [ ] 3 份文件 × 20+ 标注，进回归测试集
- [ ] Recall > 90%（改进前基线）
- [ ] 定位并修复至少 3 个主要误报根因
- [ ] 0 条未解决的规则冲突

## 关键设计决策（参考资料结论 + 评审调整）

1. **为什么 Recall > 95% 是铁律** — 漏检 = Agent 永远不会审这个条款；误报 = Agent 多审一个条款（几秒 + 几个 token）。代价完全不对等
2. **为什么引擎不过度设计** — 100 规则 × 500 clauses = 50000 次 `is_match` < 1ms；规则达 10000+ 前简单循环足够。时间花在规则质量上
3. **为什么正则和关键词互补** — 正则捕获"句式"，关键词捕获"语义"；只用正则漏同义词表达，只用关键词漏句式变化
4. **规则引擎 vs Agent 分工** — 能用"是/否"回答 → 引擎；需语义理解 → Agent。引擎产出不是终端报告，是 Agent 的上下文
5. **AI 辅助不替代人工** — AI 盲区约 29%（跨条推断 / 行业知识 / 案例关联），规则质量核心资产需人工维护
6. **为什么测试先行** — 编码前确定三层测试内容（单元 / 回归 / 盲测），TDD 约束引擎与规则行为，避免"代码先成型、测试后补"导致泛化未知
7. **为什么真实标书盲测收尾** — 开发集指标好 ≠ 泛化好；用来源零重叠的真实标书盲测验证泛化能力，按盲测意见修改规则，形成"开发集回归守门 + 盲测集验收"闭环
8. **盲测集冻结纪律** — 盲测集不参与调优，SHA-256 校验 + 一次冻结一次正式运行（对齐 `benchmark/blind-v2`）；修改验证用独立盲测集（blind-b），不追平盲测原句
